# 16 November 2026 — TryHackMe: UnrealIRCd backdoor lab

I worked through an UnrealIRCd lab over the TryHackMe OpenVPN connection. This session helped me connect the steps I had been learning separately: checking the VPN interface, scanning a host, researching a service, selecting a Metasploit module and understanding what a successful reverse shell looks like.

I am keeping the target address, flag values and credential-like material out of this public note. The work below was performed against the assigned TryHackMe lab target.

## 1. Confirming the VPN interface

I checked my network interfaces:

```bash
ip -br addr
```

The `tun0` interface was UP and had an IPv4 address assigned by the lab VPN. My Wi-Fi interface had a separate private LAN address. For a reverse connection in this VPN lab, the relevant callback address was the address on `tun0`, not the Wi-Fi address.

## 2. Reconnaissance

I checked that the lab host was reachable, then ran:

```bash
nmap <lab-target>
```

The scan showed two open TCP ports:
- `22/tcp` — SSH
- `6667/tcp` — IRC

This was a basic port scan, so it identified the services by their common port numbers but did not establish the exact software version. I should use service/version detection when I need to confirm that:

```bash
nmap -sV -p 22,6667 <lab-target>
```

## 3. Searching for known UnrealIRCd issues

I searched the local Exploit-DB index:

```bash
searchsploit UnrealIRC
```

The results included:
- UnrealIRCd 3.2.8.1 backdoor command execution (Metasploit module)
- Local configuration stack overflow
- Remote downloader/execute
- Remote denial of service

I learned that SearchSploit's path is the location of a public exploit reference; it is not itself proof that the target is vulnerable. The Metasploit Ruby module and the standalone Perl script are separate implementations.

## 4. Metasploit configuration and the port-binding mistake

I selected the UnrealIRCd backdoor module and checked its options with:

```text
search UnrealIRCd
use exploit/unix/irc/unreal_ircd_3281_backdoor
show options
```

The target service port was 6667. I initially set the reverse handler to local port 443. The first attempt failed before a session could be created:

```text
Errno::EACCES: Permission denied - bind(2) for 0.0.0.0:443
```

This was a local listener bind-permission problem. On Linux, binding to ports below 1024 normally requires elevated privileges. It did not mean that the remote exploit had succeeded.

I changed the listener to an unprivileged port (4444) and retried in the authorised lab. The handler started and the module reported that a command shell session had opened.

## 5. Verifying the shell and identity

There was an important prompt/context mistake during the first attempt. Before a session existed, I typed `whoami` at the Metasploit module prompt. Metasploit ran it locally, and it returned my local account name.

After the reverse command shell opened, I ran `whoami` in the session and it returned `webmaster`. That confirmed I was now interacting with a shell on the lab target, as a different user.

I listed the current directory and saw files and folders belonging to the UnrealIRCd installation. I then read the lab user's flag file. I am deliberately not copying the flag value into this public repository.

**Lesson:** a command typed at the `msf` prompt is not automatically a command on the remote host. I need to confirm that a session is open and interact with that session before interpreting command output as remote evidence.

## 6. Further access check

During the same lab, I found a credential-like entry in a system file. I am not recording its contents here because passwords, hashes and other authentication material do not belong in a public learning journal.

I then successfully authenticated to the lab machine over SSH as `root` and verified access by listing the root home directory and reading the lab's root-level flag file. The flag value and credential are intentionally omitted.

This note records the observed access result, not a complete explanation of the credential discovery or a general privilege-escalation technique. I need to revisit the exact permissions and authentication configuration in a controlled lab before claiming I understand why that credential was exposed.

## What I learned

- The VPN callback address must come from the VPN interface (`tun0`) when the lab target needs to reach my machine through the TryHackMe tunnel.
- A target port (`RPORT`) and a local callback port (`LPORT`) serve different purposes.
- A failed handler bind is a local listener problem; read the exact error before changing exploit settings.
- SearchSploit helps locate known exploit references, while service/version enumeration helps decide whether a result matches the target.
- A Metasploit module, payload and handler are different parts of the workflow.
- I must distinguish the local Metasploit prompt from an established remote shell.
- A shell as `webmaster` and a later authenticated SSH login as `root` are separate access observations. I should not describe them as one automatic escalation without evidence of the steps connecting them.
- Never publish lab flags, passwords, hashes or other secrets in a public repository.

## Mistakes and things to revisit

- I first tried to use privileged port 443 for the handler and got `EACCES`.
- I ran `whoami` before a session existed and initially misunderstood the local output.
- I accidentally typed a path with missing/incorrect separators while navigating to the flag file; using an absolute path avoided that issue.
- My basic Nmap scan showed the IRC port but did not verify the exact service version. I should run `-sV` and record the result separately.
- I need to understand how the credential-like file was readable and how SSH root authentication was possible, without retaining the secret itself.
