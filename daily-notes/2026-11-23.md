## 2. Web directory and upload observations

During the authorized lab exercise, I inspected the web application and observed:

- `/panel/` — the upload interface.
- `/uploads/` — a directory listing for uploaded files.
- The uploaded `rs.sh` file appeared in the uploads directory.
- Opening the `.sh` URL in the browser displayed the script as text.

### What this taught me

Uploading a file is not the same as executing it. Apache can serve a shell script as a static file; it does not automatically invoke Bash just because the file has a `.sh` extension.

A Bash script needs a shell interpreter on the server and a process or vulnerability that causes the server to execute it. Merely visiting its URL does not provide that execution.

## 3. Upload validation versus server execution

The application rejected a file with a `.php` extension during my test.

These are separate questions:

1. **Upload validation:** Does the application accept the submitted file?
2. **Storage and retrieval:** Where is the file stored, and can it be fetched?
3. **Execution:** Does the server interpret the uploaded file as executable code?

A successful upload only demonstrates that a file was stored. It does not prove that the file can execute.

## 4. Commands and concepts reviewed

Windows network inspection:

```cmd
ipconfig
route print
```

Linux file and permission concepts reviewed:

```bash
ls -l <filename>
chmod +x <filename>
```

These Linux commands must be run in an authorized Linux shell; they cannot be run against a web URL from Windows CMD.

## 6. Key lesson

A reverse shell is a way to receive an interactive connection after code execution has been achieved. It is not, by itself, an initial-access vulnerability. First understand the upload mechanism, the server's handling of files, and whether there is a legitimate path to server-side execution.
